01EC × 在庫 リアルタイム連携スタック

既存「日次連携」と「シエラ専用リアルタイム層」の役割分担

会話実行レイヤー（Planner→Executor→Validator）／チャットUI／バスケット同期／決済
★ カンリー版Sparkly内製

秒間100API以内で在庫差分同期／カゴ落ち防止／取り置き予約
★ 新規開発

API or SFTP / 1ファイル5GB / 5カラム（storeCode/offerId/price/availability/quantity）

核心の論点（Open Q4）：LAYER 3「リアルタイム同期」は新規開発が必要。 既存ベンダー（CSV日次バッチ）の上にシエラ専用の差分同期APIを載せる設計。 Walmart Sparky型「バスケット同期＋まとめ取り置き」を実現するためには LAYER 3 が不可欠。

05米国Sparky からの学習ポイント（失敗教訓含む）

Walmart Instant Checkout 失敗 → Sparky 再構築の経緯

🚨 教訓1：単品Checkoutは失敗する

2025/9 OpenAI×Walmart Instant Checkout は「単一商品ごとのチェックアウト」モデルで CVRが既存サイト1/3 に低下。 Daniel Danker（Walmart）：「消費者はアプリで日替わりに複数商品を追加し、最終的にまとめてチェックアウトする」。
→ カンリー版Sparklyは 初手から「バスケット同期＋まとめ取り置き」を必須要件として設計 すべき（LAYER 3 リアルタイム同期層の必然性）。

🌐 教訓2：Universal Commerce Protocol への準拠

Walmart×Target×Google が共同開発した Universal Commerce Protocol（REST/JSON-RPC）で、AIエージェントと小売在庫・価格・チェックアウトを標準化接続。 Mastercard×Google の Verifiable Intent（暗号学的購入認可証明）も登場。
→ カンリーは Google認定パートナー（LFP）として、この標準化の最前線に既にいる。シエラはこのプロトコル上に乗る設計が将来の選択肢を広げる。

💰 教訓3：成果報酬型 (Outcome-based) 課金で稟議が通る

Sierra標準は「解決した分だけ課金、未解決は基本無償」。SaaS座席課金（使われないライセンス料）への対案として、CFOにも説明しやすい構造。
→ カンリー版Sparkly も 「成果連動課金」設計 を初手から組み込む。既存顧客の月次レポートに「シエラ自律解決件数」を追加して連動。
